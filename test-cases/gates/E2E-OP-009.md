# E2E-OP-009: «Check before submitting» із провалом TIME_WINDOW (curfew KBP-CTR-3) → заявка лишається у стані DRAFT

**Doc ref:** `SD/04 — Frontend Scope#Operator portal`, `SD/03 — API Contract#Flight requests`, `SD/02 — Request Lifecycle#States`, `SD/06 — Business Rules#1.4 TIME_WINDOW`, `components/FlightRequestPanel.tsx`
**Role(s):** Operator (L2, ACTIVE) — залогінений
**Preconditions:**
- Оператор з `authorisation_level` = `L2` і `status` = `ACTIVE` залогінений.
- Пілот цього оператора: `rating` = `R_ADVANCED`, `certified_on` = дата за 2 місяці до `window_start`.
- ЛА цього оператора: `mtom_grams` = `3200` (смуга `C1`).
- Заявка у `DRAFT` для цього пілота й ЛА: `zone_code` = `KBP-CTR-3`, `requested_altitude_metres` = `110`, `window_start` = 02:00 місцевого часу зони дати, що настає через 7 днів, `window_end` = 02:45 того ж дня (45 хвилин; усе вікно всередині curfew).
- Браузер працює в часовому поясі `Europe/Kyiv`.

**Steps:**
1. Відкрити сторінку деталей цієї заявки `/operator/requests/<id>`.
2. Натиснути `flight-request-validate-button`.

**Expected result:** `flight-request-detail-state` показує `DRAFT`.

**Rationale:** AC SKY-1 №4. За `SD/04#Operator portal` кнопка «Check before submitting» викликає `validate` і показує результат «without changing state»; за `SD/03#Flight requests` (endpoint 13) `validate` ніколи не змінює стан (на відміну від `submit`, який при провалі гейта переводить заявку в `REJECTED`, `SD/02#Request Lifecycle`). Перевірка стану після провалу гейта показує, що `validate` не діє як `submit`. Ознака стану — `data-testid` `flight-request-detail-state` із коду.
