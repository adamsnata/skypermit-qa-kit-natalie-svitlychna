# postman-collection-builder

З API-кейсів і `../skypermit/public/openapi.yaml` будує **нову** колекцію та environment у Postman. Нічого не запускає: після створення віддає список запитів і асертів на рев'ю.

## Заборони (діють завжди)

- **Існуючі колекції й environment не змінювати й не видаляти.** Не викликати `put*`, `update*`, `delete*`, `duplicate*`, `sync*`. Дозволені лише `get*` (зокрема `getWorkspaces`) і `create*`.
- **Нічого не запускати:** ні Postman CLI, ні `Send` у застосунку, ні mock. Запуск — це скіл `postman-cli-run` і лише за явною командою користувача.
- **Секрети лише змінними environment типу secret** (`type: "secret"`) із порожнім значенням. Пароль, токен чи ключ — ні в тілі запиту, ні в скрипті, ні в описі, ні в чаті, ні у файлі `api-automation/`. У тілі запиту — `{{operatorPassword}}`.
- `../skypermit` — лише читання (Read, і лише `public/openapi.yaml`). Нічого не створювати поза цим репозиторієм і Postman.
- Очікувані значення брати **лише з кейса** (Expected result). Кейс мовчить про код чи поле → не вигадувати: або не додавати цей асерт і винести у «Відкриті питання», або позначити `TODO`.

## Крок 0. Вхід

Вхід — JSON-аргумент `{"key": "SKY-2", "files": ["test-cases/api/..."], "collection_name": "SKY-2 ..."}`:
- `key` — ключ задачі Jira (`SKY-2`); іде в назву/опис колекції й у файл списку на рев'ю;
- `files` — шляхи до файлів кейсів (за потреби з `*`, їх розгортає `Glob` лише в `test-cases/**`);
- `collection_name` — назва колекції (і основа назви environment);
- `workspace_id` — опційно; якщо не передано, шукай за назвою (п. 4).

Бракує будь-якого з полів або `files` порожній → запитай, не вгадуй.

1. Прочитай кейси з `files` (`Read`, лише `test-cases/**`). Для кожного візьми `case_id` із заголовка (`# API-OP-001: …` → `API-OP-001`), Role, Preconditions, Steps, Expected result.
2. Файл без `POST|GET|… /api/v1/…` у кроках — не API-кейс; пропусти й назви його у звіті.
3. Прочитай `../skypermit/public/openapi.yaml` (Read): шляхи, методи, поля тіл запитів, схеми відповідей, коди. Тіло запиту будуй зі схеми, а не з пам'яті.
4. Workspace: якщо `workspace_id` передано, візьми його. Інакше `getWorkspaces` і пошук за назвою «SkyPermit» (без урахування регістру, збіг за підрядком у назві).
   - Знайдено рівно один — використай його (назву й ID покажи у звіті).
   - Не знайдено або знайдено кілька — запитай користувача, який саме ID використати. Не вгадуй.

## Крок 1. Перевірка, що нічого не буде зачеплено

1. `getCollections` (workspace) і `getEnvironments`.
2. Колекція з такою самою назвою вже є → **нічого не створюй** (ні колекцію, ні environment, ні файл списку) і не дописуй у наявну. Знайди environment з назвою `<назва колекції> — local`. Покажи знайдене й запропонуй: прогнати наявну колекцію (`postman-cli-run`) або створити нову з іншою назвою (наприклад, із суфіксом дати). Останнім рядком виведи JSON без обгортки в кодовий блок:
   `{"key":"SKY-2","status":"exists","collection_id":"<uid>","environment_id":"<uid або null, якщо environment з такою назвою не знайдено>","collection_name":"…"}`
3. Колекції немає, але environment з такою назвою є → **зупинись** текстом (JSON не виводь), запропонуй іншу назву: чужий environment не використовуємо й не перезаписуємо.

## Крок 2. Відбір кейсів: готові чи «потрібна підготовка даних»

Для кожного кейса перевір, чи його Preconditions можна створити через API:

- **Оператор L1** — можна: `POST /operators` завжди створює L1.
- **Оператор L2/L3 або `SUSPENDED`** — **не можна.** За `SD/03 — API Contract#Authentication & authorisation` реєстрація завжди дає `L1`, а підвищення рівня — «out-of-band admin action». Готового L2-оператора для тестів у README, Confluence `SD` і `../skypermit/supabase/seed.sql` немає (перевірено 2026-11-10; seed містить лише зони). Такі кейси **не будують** і **не вигадують обхід** (не пробують змінити рівень, не лізуть в БД). Позначають як **«потрібна підготовка даних»** із переліком, чого бракує.
- Пілоти, борти, заявки зі станом `DRAFT` — можна створити запитами в межах кейса.
- Передумова, яку API не дає створити (інші користувачі, час доби, стан зони), — теж «потрібна підготовка даних».

## Крок 3. Environment

`createEnvironment` у workspace. Назва: `<назва колекції> — local`.

- `baseUrl` — `https://skypermit.vercel.app/api/v1` (звір із `servers` в openapi).
- Секрети (типу `secret`, значення порожні): щонайменше `operatorPassword`.
- Службові змінні для ланцюжків (`operatorId`, `pilotId`, `aircraftId`, `flightRequestId`, …) — без значень, їх заповнюють скрипти.
- Значення секретів користувач задає сам (див. `postman-cli-run`).

## Крок 4. Колекція

`createCollection` (формат Collection v2.1). Один **folder на кейс**: `<case id>: <короткий заголовок>`. Усередині — запити, **кожен** з назвою `<case id>: <що робить>` (приклад: `API-OP-001: POST /operators — реєстрація`, `API-OP-001: POST …/submit → 422`). Префікс `<case id>:` обов'язковий: за ним `postman-cli-run` зіставляє результат із кейсом.

Структура кейса:
1. Запити підготовки (реєстрація оператора, пілот, борт, заявка) — з даних Preconditions; кожен із **тестом на статус** (`201`), id зберігають у змінні environment.
2. Запит, що перевіряється (кроки кейса).

Дані: унікальні для кожного прогону (`Date.now()` в pre-request), вигадані тестові. Реквізити в тілах — змінні (`{{operatorEmail}}`, `{{operatorPassword}}`).

### Правила скриптів

- **Pre-request першого запиту:** перевірка, що секрет заповнений, інакше зрозуміла помилка без значення:
  `if (!pm.environment.get('operatorPassword')) throw new Error('Заповніть secret-змінну operatorPassword …')`.
- **Тести — у кожному запиті, обидва типи:**
  - на **статус** (`pm.response.to.have.status(…)`) — код із Expected result кейса;
  - на **тіло** (`pm.response.json()` і `pm.expect(body.<поле>)…`) — поля з Expected result (наприклад, `failing_gate`, `rule_reference`). Точне порівняння лише для значень, зафіксованих у кейсі. Для `message` перевіряй «непорожній рядок», якщо точний текст у docs не зафіксований.
- **Сесія оператора.** Cookie сесії задає Supabase (ім'я не `session`). Наявність сесії перевіряй заголовком: `pm.response.headers.has('Set-Cookie')`, а не `pm.cookies.has(...)`.
- Парсинг тіла роби обережно: якщо статус не той, `pm.response.json()` може кинути виняток. Статус перевіряй першим.
- Скрипти без секретів і без `console.log` значень змінних.

Кожний запит додай з коротким `description`: Doc ref кейса.

### Формат `url` запиту (обов'язково)

`url` кожного запиту передавай **повним об'єктом** `raw` + `host` + `path`, як у робочій колекції «SKY-2 lead time» (перевірено через `getCollection` 2026-11-10; вона проганялась через Postman CLI без помилок):

```json
"url": {
  "raw": "{{baseUrl}}/flight-requests/{{flightRequestId}}/submit",
  "host": ["{{baseUrl}}"],
  "path": ["flight-requests", "{{flightRequestId}}", "submit"]
}
```

- `host` — масив з одного елемента `{{baseUrl}}`; `path` — масив сегментів після `{{baseUrl}}` (без початкового `/`, змінні шляху на кшталт `{{flightRequestId}}` — окремим сегментом).
- `raw` = `host` + `/` + сегменти `path`, збігається з ними дослівно.
- **Не передавай `url` лише з `raw`** (`{"raw": "…"}`) і не передавай голий рядок: у колекції «SKY-2 · API» (2026-11-10) так створені `url` збереглися як `{"raw": ""}`, і Postman CLI впав на всіх запитах із `runtime: request url is empty`.

## Крок 4а. Перевірка колекції після створення (обов'язкова)

Одразу після `createCollection`, **до** кроку 5 і до будь-якого повідомлення про готовність:

1. `getCollection` (`collectionId` = uid створеної колекції, `model: "full"`).
2. Обійди всі запити (рекурсивно, через вкладені `item`) і для кожного перевір `request.url`:
   - `url` — об'єкт, `raw` непорожній рядок;
   - `host` — непорожній масив, `path` — непорожній масив;
   - `raw` починається з `{{baseUrl}}`.
3. Усе гаразд — іди до кроку 5.
4. Хоч один запит не пройшов перевірку → **зупинись**: не пиши файл списку, не виводь JSON зі `status: "created"` і не пропонуй запуск. Поясни текстом: uid колекції, скільки запитів із N не пройшли й назви перших трьох, що саме не так (порожній `raw`, немає `host`/`path`). Колекцію не змінюй і не видаляй (діють «Заборони»); запропонуй створити нову з іншою назвою й виправленим `url`.

## Крок 5. Зупинка й список на рев'ю

Нічого не запускай. Збережи список у `api-automation/collections/<назва колекції>.md` (українською; папку створи при першому записі). Структура файла:

```
# Колекція «<назва>» — список на рев'ю
Колекція: <uid> · Environment: <uid> · Workspace: <назва> · Дата: <дата>

## Запити й асерти
| Запит | Кейс | Метод і URL | Асерти (статус / тіло) |

## Кейси, які потрібно підготувати («потрібна підготовка даних»)
| Кейс | Чого бракує | Чому не можна створити через API |

## Відкриті питання
(де кейс чи docs мовчать)

## Мапа кейсів
| case_id | статус | запитів |   ← статус: ready | needs-data
```

Таблицю «Мапа кейсів» читає `postman-cli-run`, не змінюй її формат.

У чаті поверни те саме стисло: назва й uid колекції та environment, таблиця запитів з асертами, кейси «потрібна підготовка даних», відкриті питання. Закінчи фразою, що нічого не запускалось і що для запуску потрібен `postman-cli-run` та ваша явна команда.

Останнім рядком відповіді виведи JSON без обгортки в кодовий блок (його читає оркестратор):

`{"key":"SKY-2","status":"created","collection_id":"<uid>","collection_name":"…","environment_id":"<uid>","workspace":"<назва>","ready":["API-OP-011"],"needs_data":[{"case_id":"API-OP-012","missing":"оператор L2"}],"skipped_files":["…"],"open_questions":["…"]}`

`ready` і `needs_data` збігаються з таблицею «Мапа кейсів». `status: "exists"` виводиться лише на кроці 1 (див. там). Зупинка до створення з інших причин (є лише environment, не знайдено workspace, бракує полів), а також зупинка на кроці 4а (колекцію створено, але `url` запитів некоректні) — JSON не виводь, поясни текстом.

## Чого скіл не робить

- Не запускає колекцію й не виправляє її після створення (правки — за окремою командою).
- Не змінює файли кейсів у `test-cases/` і не пише в `../skypermit`.
- Не створює кейси й не верифікує їх (це інші скіли).
- Не синхронізує зі Testomat.io (це `testomat-sync`).
