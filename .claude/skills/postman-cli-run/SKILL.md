# postman-cli-run

Запускає колекцію через Postman CLI, пише лог і повертає pass/fail по кожному кейсу. Прогін створює дані на `https://skypermit.vercel.app` (оператор, пілот, борт, заявки), тому скіл викликається лише вручну й лише після явної команди.

## Заборони (діють завжди)

- **Не запускати без явного «запускай»** користувача, сказаного в цій розмові **після** того, як скіл показав, що саме запустить (крок 2). Згода на один прогін не переноситься на наступний. Слова «ок», «добре», «давай» без «запускай» — не команда: перепитай.
- **Нічого не виправляти, щоб тест пройшов:** не змінювати колекцію, environment, кейси, тіла й асерти, не підганяти дані, не перезапускати, поки не зеленіє. Падіння — це результат: опиши його й запропонуй правку текстом, внести її можна лише за окремою командою.
- **Секретні значення не виводити:** ні в чат, ні у звіт, ні в команду (у команді — лише ім'я змінної ОС). Не просити користувача вставляти пароль у чат. Скіл не має інструментів для редакції логів (немає `awk`/`sed`), тому:
  - **ніколи не відкривай `*.collection-run-executions.yaml`** (Read, у чаті, у звіті): він містить тіла запитів, зокрема пароль оператора, і cookie сесії (див. крок 3);
  - `*.collection-run-summary.yaml` читай лише щоб дочитати подробиці падіння, і не цитуй із нього нічого, що схоже на секрет.
- **Лише дозволені команди** з `allowed-tools`: `postman collection run …` і `mkdir -p api-automation/runs`. Голого `Bash` немає: не використовуй `awk`, `tee`, `grep`, `pwd`, `cat`, перенаправлення виводу та інші команди. Крок, який без них неможливий, — не обходь, а повідом користувача.
- Не встановлювати пакети й утиліти (в т.ч. Postman CLI). Немає CLI — зупинись, опиши, що потрібно.
- Файли змінювати лише в `api-automation/runs/` (нові логи). Нічого в `../skypermit`.
- Не видаляти раніше записані логи.

## Передумови

### Змінна ОС `SKYPERMIT_OPERATOR_PASSWORD`

Значення secret-змінних Postman **не синхронізуються в хмару**, тож CLI їх не бачить (прогін без пароля падає в pre-request: «Заповніть secret-змінну operatorPassword»). Тому пароль передається змінною ОС `SKYPERMIT_OPERATOR_PASSWORD`; скіл підставляє її як `--env-var "operatorPassword=$SKYPERMIT_OPERATOR_PASSWORD"`.

Як задати її в Windows (робіть це **поза цим чатом**, щоб пароль не потрапив у розмову; мінімум 8 символів):

- **На один сеанс, PowerShell** (потім запустіть `claude` з цього ж вікна):
  `$env:SKYPERMIT_OPERATOR_PASSWORD = "ваш_пароль"`
- **Git Bash:** `export SKYPERMIT_OPERATOR_PASSWORD='ваш_пароль'`
- **Назавжди (для нових вікон):** `setx SKYPERMIT_OPERATOR_PASSWORD "ваш_пароль"` — діє лише в **нових** терміналах; перезапустіть термінал і Claude Code. Або через «Параметри → Система → Додаткові параметри системи → Змінні середовища».

Скіл **не може** перевірити, що змінна задана: для цього потрібен голий `Bash` (`echo`, `[ -n … ]`), якого в `allowed-tools` немає. Тому перед «запускай» попередь користувача, що змінну треба задати. Якщо вона не задана, `--env-var` отримає порожнє значення, і pre-request першого запиту зупинить прогін з повідомленням «Заповніть secret-змінну operatorPassword …»; це проблема передумов, а не кейса.

### Postman CLI

Окремої перевірки `postman --version` немає (вона не входить у дозволені команди). Немає CLI або він не залогінений — це видно з помилки першого запуску: зупинись і опиши, що потрібно. **Логін Postman CLI виконується лише в окремому терміналі**, поза сесією Claude Code: `postman login` (ключ вводиться там). Не пропонуй і не виконуй логін через `!` у цій сесії та не проси ключ у чат.

### Робоча папка

Усі шляхи (`api-automation/runs`) відносні до кореня репозиторію. Перевірити `pwd` скіл не може, тож користувач має запускати Claude Code з кореня репозиторію.

## Крок 1. Знайти колекцію й environment

Вхід — JSON-аргумент `{"key": "SKY-2", "collection_id": "<uid>", "environment_id": "<uid>"}`: `key` — ключ задачі (іде в результат), `collection_id` і `environment_id` — **uid** у форматі `<owner>-<uuid>`. Бракує будь-якого поля → запитай, не вгадуй.

1. `getCollection` (`collection_id`, `model: "full"`) і `getEnvironment` (`environment_id`): переконайся, що вони існують. Помилка або не знайдено → запитай, не вгадуй і не шукай за назвою.
2. Перелік запитів і кейсів — з `getCollection`: ID кейса береться з префікса «`<case id>:`» в назвах запитів і папок.
3. Ключ задачі — `key` з аргументу.
4. Прочитай `api-automation/collections/<назва колекції>.md` (його створює `postman-collection-builder`): таблицю «Мапа кейсів» (`case_id`, `статус` `ready | needs-data`) і розділ «Кейси, які потрібно підготувати» (чого бракує). Файла немає — працюй без мапи й скажи про це у звіті: кейси `needs-data` тоді не побачиш.

## Крок 2. Показати, що запуститься, і чекати «запускай»

Покажи: колекція (назва, uid), environment, кількість запитів, перелік кейсів, команду з ім'ям змінної (без значення), куди піде звіт, що змінну `SKYPERMIT_OPERATOR_PASSWORD` має бути задано (скіл це не перевіряє), і що прогін створить тестові дані на `https://skypermit.vercel.app` (оператор, пілот, борт, заявки; їх не видаляють). Тоді **зупинись і чекай** «запускай».

Це правило діє й при виклику з оркестратора: «запускай» має прозвучати **після** цього показу. Скіл показує крок 2 сам, оркестратор про запуск окремо не питає. Відповідь користувача, що не є «запускай» (відмова, «ок», мовчання), — прогін не відбувся: поверни `not_run` (див. крок 5).

## Крок 3. Запуск

Лише дві дозволені команди, одна за одною, без конвеєрів і перенаправлень.

1. `mkdir -p api-automation/runs`
2. ```
   postman collection run <collection-uid> -e <environment-uid> --env-var "operatorPassword=$SKYPERMIT_OPERATOR_PASSWORD" --no-report-events --output api-automation/runs
   ```

Лог пише вбудований звіт Postman CLI: `--output <folder>` створює в `api-automation/runs/` пару YAML-файлів `<колекція-slug>-<мітка часу>.collection-run-summary.yaml` і `….collection-run-executions.yaml`. Ім'я файла задати не можна. Вивід у консоль (cli-репортер) CLI дає за замовчуванням, його скіл бере з результату команди.

> **⚠ Що лежить у цих файлах.** `*.collection-run-executions.yaml` містить **тіла запитів (зокрема пароль оператора) і cookie сесії** (у попередніх прогонах це підтверджено). Тому `api-automation/runs/` у `.gitignore`; ці файли **не відкривати в чаті й не публікувати** (не додавати в git, не вставляти в Jira, Testomat чи Postman). Результати по кейсах бери **з виводу CLI** і з `*.collection-run-summary.yaml`.
>
> **Записати лише summary без executions неможливо.** У `postman collection run --help` (перевірено 2026-11-10) `--output <folder>` завжди створює обидва файли; прапорця «лише summary» чи вимкнення executions немає. `--silent` лише прибирає вивід у консоль і не допомагає (результати беруться саме з нього). Тож скіл не може гарантувати відсутність секретів у файлах на диску: лише обмежує доступ (див. «Заборони») і покладається на `.gitignore`. Файли в `api-automation/runs/` після прогону користувач за потреби видаляє вручну; скіл їх не видаляє.

> **Чому не `--reporters cli,json --reporter-json-export`.** У `postman collection run --help` (перевірено 2026-11-10) таких прапорців немає: це прапорці newman, а не Postman CLI. Найближчий вбудований репортер — `--output`.

- `--no-report-events` вимикає передачу подій прогону в конвеєри API Catalog / Application Inventory. **Не підтверджено**, що він вимикає й повідомлення «Uploading Postman CLI run data to Postman Cloud» (окремого прапорця вивантаження в `--help` немає). Якщо у виводі є рядок «Uploaded successfully», скажи про це у звіті прямо.
- Інші змінні environment (`baseUrl` тощо) CLI бере з cloud-environment за uid; змінюються вони лише скриптами під час прогону.
- Скіл **не може** перевірити, що значення секрету не потрапило у вивід або YAML (немає `grep`), і не може його відредагувати (немає `awk`). Вивід CLI значення `--env-var` досі не показував, але для `…executions.yaml` це **неправда**: там пароль і cookie є (див. примітку вище). Тому **результати бери з виводу команди**, а `Read` використовуй лише для `…summary.yaml`, щоб дочитати подробиці падіння; якщо там видно значення секрету, не цитуй його, а попередь користувача й порадь змінити пароль.

## Крок 4. Розбір по кейсах

Для кожного `<case id>` (префікс «`<case id>:`» у назвах запитів і папок):

- **pass** — усі асерти всіх запитів кейса пройшли.
- **fail** — є хоч один асерт чи помилка скрипта, що впали. Вкажи, у якому запиті (підготовка чи основний), який асерт, очікуване й фактичне (з виводу CLI).
- **skipped** — кейс зі статусом `needs-data` у мапі («потрібна підготовка даних»; у колекції його немає, `message` = «Потрібна підготовка даних: <чого бракує з розділу мапи>»), або запити кейса не виконалися (їх немає у виводі, наприклад через `--bail` чи зупинку прогону; вкажи причину).

Розбір падіння: перша причина (підготовка → каскад), а не перелік наслідків. Помилка pre-request на порожньому секреті — це проблема передумов, а не кейса. Не пропонуй і не роби змін, щоб «позеленіло».

## Крок 5. Звіт у чат

Після прогону відповідь складається з двох частин: короткого пояснення простою мовою (що створено, що впало й чому, чи був рядок про вивантаження в Postman Cloud, шлях до YAML-звіту; для кожного `fail` — найімовірніша причина й текстова пропозиція правки, нічого не застосовано) і **об'єкта за контрактом** нижче. Після реального прогону об'єкт за контрактом виводиться **останнім рядком** відповіді: один рядок JSON, без обгортки в кодовий блок. Приклад нижче показано багаторядковим для читабельності.

Якщо прогін не відбувся (немає «запускай», немає CLI чи логіну, помилка першого запуску), поясни текстом, що зупинило, а останнім рядком виведи:

`{"key":"SKY-2","status":"not_run","reason":"<що зупинило, без секретів>"}`

```json
{
  "status": "completed",
  "key": "SKY-2",
  "results": [
    { "case_id": "API-OP-001", "status": "passed", "message": "" },
    { "case_id": "API-OP-002", "status": "failed", "message": "Запит «API-OP-002: POST …/submit → 422», асерт «failing_gate = PILOT»: очікувалось PILOT, отримано AIRCRAFT" },
    { "case_id": "API-OP-003", "status": "skipped", "message": "Запити кейса не виконались: прогін зупинено" }
  ],
  "summary": { "passed": 1, "failed": 1, "skipped": 1 }
}
```

- `status` верхнього рівня — `"completed"` (прогін завершено) або `"not_run"` (прогін не відбувся; тоді лише `key` і `reason`).
- `key` — ключ задачі (крок 1, п. 3).
- `results[]` — по одному елементу на кейс: `case_id`; `status` — `passed | failed | skipped`; `message` — порожній для `passed`, обов'язковий для `failed` (що очікувалось, що отримано, запит/крок) і для `skipped` (причина). Секретів і сирих тіл відповідей у `message` немає.
- `summary` — кількість кейсів за статусами (`passed + failed + skipped` = довжина `results`).
- Поле `test_id` скіл не знає: його дає `testomat-sync upsert` (відповідність `case_id` → `test_id`).

## Чого скіл не робить

- Не будує й не змінює колекцію (є `postman-collection-builder`).
- Не викликає `mcp__testomatio__*` — результати лише готує для `testomat-sync report`.
- Не повторює прогін, поки не буде зелений, і не міняє очікування під фактичний результат.
