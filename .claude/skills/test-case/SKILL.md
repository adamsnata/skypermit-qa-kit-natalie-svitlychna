# Тест-кейс (один атомарный)

Тест-кейс — **атомарная проверка**: одно конкретное действие или условие → один конкретный ожидаемый результат. Не сценарий из десятка шагов.

## Источник и ограничения

- Спецификация: `C:\workspace\skypermit\docs\` (`01-data-model.md` … `08-uml-diagrams.md`).
- Кодовая база: `C:\workspace\skypermit\` (`app/`, `components/`, `lib/`, `supabase/migrations/`, `tests/`).
- `../skypermit` — **только чтение**. Используй Read / Glob / Grep. Ничего там не создавай, не меняй и не запускай.
- Результат пиши только в `test-cases/{module}/` этого репозитория (создай папку, если её нет).
- **Существующие файлы не меняй.** Скилл только создаёт новые файлы. Не редактируй, не переименовывай и не перенумеровывай ранее созданные кейсы в `test-cases/` и планы в `test-plans/`.
- Кейс пиши на **русском**. Названия полей шаблона — на английском, как в шаблоне. Идентификаторы из спецификации и кода (состояния, эндпоинты, поля, коды ответов, `data-testid`) оставляй как в оригинале: `DRAFT`, `POST /api/v1/requests`, `422`.

## Справочник

### Модули (`{module}`)

| Модуль | Что входит |
|---|---|
| `auth` | регистрация, login/logout/me, `401`/`403`, статус `SUSPENDED` |
| `pilots` | CRUD пилотов оператора, `rating`, `certified_on` |
| `aircraft` | CRUD ЛА оператора, `mtom`, weight band |
| `requests` | `FlightRequest`: создание, правка, submit, validate, cancel, переходы state |
| `review` | очередь ревьюера, approve/reject, `X-Reviewer-Id`, `AuditLog` |
| `gates` | гейты `PILOT` / `AIRCRAFT` / `ZONE` / `TIME_WINDOW`, `rule_reference` |

Если проверка не ложится ни в один модуль — спроси пользователя, не создавай новый модуль сам.

### Формат ID: `<УРОВЕНЬ>-<РОЛЬ>[-<РОЛЬ>]-<NNN>`

**Уровень** — через что выполняется проверка:

| Префикс | Уровень |
|---|---|
| `API` | прямой HTTP-запрос к `/api/v1/...` (без UI) |
| `E2E` | через пользовательский интерфейс (экраны оператора/ревьюера) |

Если нужен другой уровень — спроси пользователя.

**Роль:**

| Код | Роль |
|---|---|
| `OP` | Operator, в том числе регистрация, вход и выход оператора (даже если до проверяемого действия сессии ещё нет) |
| `RV` | Reviewer |
| `AN` | неавторизованный пользователь, который обращается к защищённому ресурсу без сессии и без `X-Reviewer-Id` (например, проверка `401`) |

- Если в кейсе действуют две роли — пропиши **обе** в порядке их действий: `E2E-OP-RV-001`.
- **Номер** — три цифры. ID уникален во **всём** `test-cases/` (по всем модулям). Следующий номер = максимальный существующий номер для того же префикса (`<УРОВЕНЬ>-<РОЛИ>`) + 1; если таких нет — `001`.
- Пропуски в нумерации **не заполняй и не исправляй**. Главное — нет дублей.

## Шаг 1. Определи модуль, уровень и роль(и)

По запросу пользователя определи модуль, уровень (`API` / `E2E`) и роль(и). Если что-то из этого нельзя однозначно вывести — спроси одним вопросом.

## Шаг 2. Посмотри, что уже есть

1. Glob `test-cases/**/*.md` — все существующие кейсы. Папку `test-cases/_reviews/` (отчёты агента `tc-verifier`) пропускай: это не кейсы, их ID в нумерации не участвуют.
2. Прочитай кейсы модуля `test-cases/{module}/` — выпиши, какие проверки уже покрыты (по заголовку и Expected result).
3. Найди максимальный номер для нужного префикса по всем модулям → следующий номер.

## Шаг 3. Выбери режим

- **Запрос называет конкретную проверку** («submit с пилотом без рейтинга → 422 PILOT») — если такой проверки ещё нет, создавай сразу (шаг 4). Если уже есть — сообщи ID существующего кейса и ничего не создавай.
- **Назван только модуль/функция** («кейсы для pilots», «проверь cancel») — предложи 4–6 атомарных проверок, которых ещё нет: позитивная + негативные + граничные. Для каждой: уровень, роль(и), одна строка «действие → результат», Doc ref. Спроси через AskUserQuestion, какую создать.
- **Ответить некому** (неинтерактивный запуск) — создай позитивную проверку (happy path), если её ещё нет; если есть — первую из предложенных негативных.

## Шаг 4. Собери источники

- Прочитай нужные разделы `docs/` целиком и **обязательно** сверь с `05-open-questions.md` и `07-clarifications.md`:
  - вопрос разрешён в `07` — используй решение и добавь его в Doc ref;
  - вопрос открыт — не придумывай поведение, поставь `TODO: уточнить по требованиям (<Q-id или суть вопроса>)`.
- Из кода бери то, что нужно для **шагов**: маршруты страниц (`app/operator/...`, `app/reviewer/...`), эндпоинты (`app/api/v1/...`), `data-testid`, названия кнопок и полей, логику гейтов (`lib/gates`).
- **Ожидаемый результат — по документации.** Если код расходится с `docs/`, пиши кейс по документации, а расхождение укажи в Rationale строкой `Расхождение с кодом: <файл> — <что отличается>`.
- **Не придумывай тексты ошибок, коды и лимиты.** Бери их дословно из Doc ref. Если в документации их нет — спроси пользователя или поставь `TODO: уточнить по требованиям`.

## Шаг 5. Проверь атомарность

- Одно проверяемое действие/условие и **один** ожидаемый результат (он может состоять из нескольких наблюдаемых признаков одного исхода, например код `422` + `gate` в теле).
- Steps — не больше 5 шагов; последний шаг — проверяемое действие.
- Всё, что лишь готовит данные (оператор с нужным уровнем, пилот, ЛА, заявка в нужном state), — в Preconditions, а не в Steps.
- Конкретные значения вместо общих слов: `mtom = 30001 г`, а не «большая масса».
- Если проверка распадается на две — создай одну, а вторую предложи пользователю отдельно.

## Шаг 6. Запиши файл

Путь: `test-cases/{module}/<ID>.md`, например `test-cases/gates/API-OP-003.md`. Перед записью убедись, что такого файла нет.

- Шаблон: `templates/test-case.md` (рядом с этим `SKILL.md`) — прочитай, скопируй и заполни. Поля — ровно как в шаблоне и в том же порядке: заголовок `# <ID>: …`, Doc ref, Role(s), Preconditions (опционально), Steps, Expected result, Rationale. Новых полей не добавляй.
- Образцы готовых кейсов: `example/` — `E2E-OP-001.md` (E2E, happy path) и `API-OP-001.md` (API, негативный, с `TODO`). Сверяй с ними стиль и детализацию. ID в `example/` не участвуют в нумерации — следующий номер ищи только в `test-cases/`.

### Правила заполнения

- **Заголовок:** коротко, в формате «условие → результат», например `Submit с ЛА mtom = 30001 г → 422`.
- **Doc ref:** минимум одна ссылка на `docs/` в формате `doc#section`; ссылки на код допустимы дополнительно.
- **Role(s):** для оператора указывай `authorisation_level` и `status`, если они влияют на результат.
- **Expected result:** без «корректно», «успешно», «как ожидается» — только наблюдаемый факт.

## Шаг 7. Отчёт пользователю (на русском)

Коротко:
- путь к файлу и ID;
- Doc ref;
- есть ли `TODO: уточнить по требованиям` и расхождения с кодом;
- 1–3 соседние атомарные проверки, которых ещё нет, — как предложение для следующих кейсов.
