# UI тест-кейси (атомарні)

Тест-кейс — **атомарна перевірка**: одна конкретна дія або умова → один конкретний очікуваний результат. Не сценарій із десятка кроків.

> **Тимчасово:** API-кейси й режим "Дано правило" лишаються тут для cover-gaps, доки не з'явиться api-test-case-creator. Тоді перенести їх туди й переключити cover-gaps.

## Джерело та обмеження

- Специфікація: Confluence, простір `SD` (cloudId `04cfe3ba-ca1f-4d3c-8ff3-b67f1f3c5083`), сторінки `01 — Data Model` … `08 — UML Diagrams`; pageId — у `CLAUDE.md`. Читай через `getConfluencePage`, лише читання.
- Кодова база: `C:\workspace\skypermit\` (`app/`, `components/`, `lib/`, `supabase/migrations/`, `tests/`) — для `data-testid`, маршрутів, ендпоінтів, логіки гейтів.
- `../skypermit` — **лише читання**. Використовуй Read / Glob / Grep. Нічого там не створюй, не змінюй і не запускай.
- Результат пиши лише в `test-cases/{module}/` цього репозиторію (створи папку, якщо її немає).
- **Наявні файли не змінюй.** Скіл лише створює нові файли. Не редагуй, не перейменовуй і не перенумеровуй раніше створені кейси в `test-cases/` і плани в `test-plans/`.
- Кейс пиши **українською**. Назви полів шаблону — англійською, як у шаблоні. Ідентифікатори зі специфікації та коду (стани, ендпоінти, поля, коди відповідей, `data-testid`) залишай як в оригіналі: `DRAFT`, `POST /api/v1/requests`, `422`.

## Довідник

### Модулі (`{module}`)

| Модуль | Що входить |
|---|---|
| `auth` | реєстрація, login/logout/me, `401`/`403`, статус `SUSPENDED` |
| `pilots` | CRUD пілотів оператора, `rating`, `certified_on` |
| `aircraft` | CRUD ЛА оператора, `mtom`, weight band |
| `requests` | `FlightRequest`: створення, редагування, submit, validate, cancel, переходи state |
| `review` | черга рецензента, approve/reject, `X-Reviewer-Id`, `AuditLog` |
| `gates` | гейти `PILOT` / `AIRCRAFT` / `ZONE` / `TIME_WINDOW`, `rule_reference` |

Якщо перевірка не вписується в жоден модуль — запитай користувача, не створюй новий модуль сам.

### Формат ID: `<РІВЕНЬ>-<РОЛЬ>[-<РОЛЬ>]-<NNN>`

**Рівень** — через що виконується перевірка:

> **Тимчасово:** API-кейси й режим "Дано правило" лишаються тут для cover-gaps, доки не з'явиться api-test-case-creator. Тоді перенести їх туди й переключити cover-gaps.

| Префікс | Рівень |
|---|---|
| `API` | прямий HTTP-запит до `/api/v1/...` (без UI) |
| `E2E` | через інтерфейс користувача (екрани оператора/рецензента) |

Якщо потрібен інший рівень — запитай користувача.

**Роль:**

| Код | Роль |
|---|---|
| `OP` | Operator, зокрема реєстрація, вхід і вихід оператора (навіть якщо до перевірюваної дії сесії ще немає) |
| `RV` | Reviewer |
| `AN` | неавторизований користувач, який звертається до захищеного ресурсу без сесії та без `X-Reviewer-Id` (наприклад, перевірка `401`) |

- Якщо в кейсі діють дві ролі — пропиши **обидві** в порядку їхніх дій: `E2E-OP-RV-001`.
- **Номер** — три цифри. ID унікальний у **всьому** `test-cases/` (за всіма модулями). Наступний номер = максимальний наявний номер для того самого префікса (`<РІВЕНЬ>-<РОЛІ>`) + 1; якщо таких немає — `001`.
- Пропуски в нумерації **не заповнюй і не виправляй**. Головне — немає дублів.

## Крок 1. Визнач модуль, рівень і роль(і)

За запитом користувача визнач модуль, рівень (`API` / `E2E`) і роль(і). Якщо щось із цього не можна однозначно вивести — запитай одним питанням.

## Крок 2. Подивися, що вже є

1. Glob `test-cases/**/*.md` — усі наявні кейси.
2. Прочитай кейси модуля `test-cases/{module}/` — випиши, які перевірки вже покриті (за заголовком і Expected result).
3. Знайди максимальний номер для потрібного префікса за всіма модулями → наступний номер.

## Крок 3. Обери режим

- **Запит називає конкретну перевірку** («submit з пілотом без рейтингу → 422 PILOT») — якщо такої перевірки ще немає, створюй одразу (крок 4). Якщо вже є — повідом ID наявного кейсу й нічого не створюй.
- **Названо лише модуль/функцію** («кейси для pilots», «перевір cancel») — запропонуй 4–6 атомарних перевірок, яких ще немає: позитивна + негативні + граничні. Для кожної: рівень, роль(і), один рядок «дія → результат», Doc ref. Запитай через AskUserQuestion, яку створити.
- > **Тимчасово:** API-кейси й режим "Дано правило" лишаються тут для cover-gaps, доки не з'явиться api-test-case-creator. Тоді перенести їх туди й переключити cover-gaps.

  **Дано правило** (JSON зі скрипта `scripts/uncovered-rules.mjs`: `id`, `gate`, `title`, `citation`, `open`; опційно `reserved_ids` — ID, уже згенеровані в цьому прогоні й ще не записані) — AskUserQuestion не викликай і **файли не записуй**: поверни згенерований кейс, а гейт людини виконує cover-gaps пакетно по всіх правилах. Номер ID обирай з урахуванням `reserved_ids`:
  - модуль = `gates`; рівень = `API`; роль = `OP` (якщо правило не вимагає іншої — тоді `RV`);
  - `open: true` → кейс **не створюй**, поверни статус `open_question` (див. «Крок 7»);
  - створи **один** негативний кейс: порушення правила → `422`, `failing_gate = <gate>`, `rule_reference = <citation>` (значення дослівно з `06 — Business Rules` §6);
  - позитивні й граничні кейси цього правила не створюй, лише запропонуй у звіті.
- **Дано задачу** (вхід від оркестратора `story-to-tests`: JSON від `jira-intake` + `doc_check` — таблиця статусів AC від `story-doc-check`; опційно `reserved_ids` і `revise: {"paths":[…],"comments":"…"}`) — AskUserQuestion не викликай, гейт людини не виконуй: його виконує оркестратор. Файли **записуй одразу** як чернетки (крок 6, з валідацією хука).
  - Рівень = `E2E`; роль — з AC і Doc ref (за замовчуванням `OP`); модуль — з довідника. Якщо модуль чи роль не виводяться однозначно — нічого не записуй і поверни `status: "needs_input"` з питанням у `reason`.
  - Добери повний набір за техніками (EP / BV / state transition, див. нижче) лише для AC зі статусом «покрито». AC «не описано» — кейс лише якщо перевірка конкретна, а очікуваний результат ставиться як `TODO: уточнити за вимогами`; інакше AC іде в `skipped`. AC «суперечить» — кейс не створюй, AC іде в `skipped`.
  - У Rationale кожного кейса додай рядок `Задача: <key>, AC <номери>`. Нових полів не додавай.
  - З `revise`: перезаписуй **лише** файли зі списку `revise.paths` (виняток із правила «наявні файли не змінюй»), застосувавши `revise.comments`. Нові кейси в цьому виклику не створюй.
  - Хук заблокував запис — кейс не повторюй, додай його в `skipped` з текстом помилки.
  - **Запис лише через Write.** Кожен кейс записуй окремим викликом інструмента Write у `test-cases/{module}/<ID>.md`. Не пиши файли через Bash, python чи PowerShell (`>`, `Set-Content`, `open(...).write` тощо): хук `validate-test-case.mjs` валідує записи через Write, а запис в обхід нього лишає кейс без перевірки. Якщо Write недоступний або відхилений, не шукай обхідний шлях: поверни `status: "failed"` з поясненням у `reason`.
- **Відповісти нікому** (неінтерактивний запуск) — створи позитивну перевірку (happy path), якщо її ще немає; якщо є — першу із запропонованих негативних.

### Техніки тест-дизайну (режим «Названо лише модуль/функцію»)

Замість 4–6 пропозицій розбери функцію за трьома техніками й підготуй **весь** потрібний набір UI/E2E-кейсів (кожен — окремий атомарний кейс, кроки через `data-testid`):
- **EP:** по одному кейсу на кожен валідний і невалідний клас еквівалентності кожного поля форми.
- **BV:** для числових/довжинних полів — значення на межі, під нею й над нею (напр. `mtom` 30000 / 30001 г); межі бери лише з Doc ref.
- **State transition:** усі дозволені переходи `FlightRequest` (`DRAFT → SUBMITTED` тощо) за `02 — Request Lifecycle`. Заборонений перехід у UI перевіряй тим, що відповідна дія недоступна в інтерфейсі: кнопка відсутня або `disabled` (за `data-testid`). Відхилення з `409` — це API-перевірка, її в UI-кейси не додавай.

Кейс, який уже покритий, не дублюй (Крок 2). Кількість кейсів у наборі вкажи у звіті.

## Крок 4. Збери джерела

- Прочитай потрібні сторінки Confluence повністю й **обовʼязково** звір із `05 — Open Questions` і `07 — Clarifications`:
  - питання розвʼязане в `07` — використовуй рішення й додай його в Doc ref;
  - питання відкрите — не вигадуй поведінку, постав `TODO: уточнити за вимогами (<Q-id або суть питання>)`.
- Для правил гейтів звіряй `gate` із `07 — Clarifications`: якщо `06` і `07` розходяться, діє `07`.
- З коду бери те, що потрібно для **кроків**: маршрути сторінок (`app/operator/...`, `app/reviewer/...`), ендпоінти (`app/api/v1/...`), `data-testid`, назви кнопок і полів, логіку гейтів (`lib/gates`).
- **Очікуваний результат — за документацією.** Якщо код розходиться зі специфікацією в Confluence, пиши кейс за документацією, а розбіжність вкажи в Rationale рядком `Розбіжність із кодом: <файл> — <що відрізняється>`.
- **Не вигадуй тексти помилок, коди й ліміти.** Бери їх дослівно з Doc ref. Якщо в документації їх немає — запитай користувача або постав `TODO: уточнити за вимогами`.

## Крок 5. Перевір атомарність

- Одна перевірювана дія/умова й **один** очікуваний результат (він може складатися з кількох спостережуваних ознак одного результату, наприклад код `422` + `gate` у тілі).
- Steps — не більше 5 кроків; останній крок — перевірювана дія.
- Усе, що лише готує дані (оператор із потрібним рівнем, пілот, ЛА, заявка в потрібному state), — у Preconditions, а не в Steps.
- Конкретні значення замість загальних слів: `mtom = 30001 г`, а не «велика маса». Значення добирай під конкретне правило; унікальні дані (email, `national_id`) роби унікальними для кейсу, наприклад з його ID.
- Якщо перевірка розпадається на дві — створи одну, а другу запропонуй користувачу окремо.

## Крок 5а. Гейт людини (усі режими)

Перед записом будь-яких файлів покажи **всі** згенеровані кейси повністю (у вигляді, в якому вони потраплять у файли) і запитай через AskUserQuestion: «Схвалити / Правити / Відхилити».
- **Схвалити** → переходь до кроку 6 і запиши файли в `test-cases/`.
- **Правити** → внеси правки користувача й покажи кейси знову з тим самим питанням.
- **Відхилити** → нічого не записуй.

Без явного «Схвалити» файли не створюються. Це діє й для режиму «Відповісти нікому». Виняток — режим «Дано задачу»: він пише чернетки без питання, а єдиний гейт «Схвалити / Правити / Відхилити» виконує оркестратор `story-to-tests`. Виняток — режим «Дано правило»: там скіл не питає й не записує, а повертає кейс (повний текст у блоці ```markdown перед JSON-рядком); єдиний гейт «Схвалити / Правити / Відхилити» для всього пакета виконує cover-gaps, і файли записує він.

## Крок 6. Запиши файл

Шлях: `test-cases/{module}/<ID>.md`, наприклад `test-cases/gates/API-OP-003.md`. Перед записом переконайся, що такого файлу немає. Записуй інструментом Write, по одному файлу за виклик (у режимі «Дано задачу» це обовʼязково, див. вище).

- Шаблон: `templates/test-case.md` (поруч із цим `SKILL.md`) — прочитай, скопіюй і заповни. Поля — рівно як у шаблоні й у тому самому порядку: заголовок `# <ID>: …`, Doc ref, Role(s), Preconditions (опційно), Steps, Expected result, Rationale. Нових полів не додавай.
- Зразки готових кейсів: `examples/` — `E2E-OP-001.md` (E2E, happy path) і `API-OP-001.md` (API, негативний, з `TODO`). Звіряй із ними лише структуру, стиль і деталізацію. У зразках навмисно немає конкретних тестових даних (email, `national_id`, пароль, рівні): конкретні значення добирай сам за правилом і Doc ref, не копіюй їх зі зразків і не повторюй однакові значення в різних кейсах. ID в `examples/` не беруть участі в нумерації — наступний номер шукай лише в `test-cases/`.

### Правила заповнення

- **Заголовок:** коротко, у форматі «умова → результат», наприклад `Submit з ЛА mtom = 30001 г → 422`.
- **Doc ref:** щонайменше одне посилання на Confluence у форматі `SD/<назва сторінки>#<розділ>`; посилання на код допустимі додатково.
- **Role(s):** для оператора вказуй `authorisation_level` і `status`, якщо вони впливають на результат.
- **Expected result:** без «коректно», «успішно», «як очікується» — лише спостережуваний факт.

## Крок 7. Звіт користувачу (українською)

Коротко:
- шлях до файлу та ID;
- Doc ref;
- чи є `TODO: уточнити за вимогами` і розбіжності з кодом;
- 1–3 сусідні атомарні перевірки, яких ще немає, — як пропозиція для наступних кейсів.

**У режимі «Дано правило»** останнім рядком відповіді виведи JSON для оркестратора (без обгортки в кодовий блок):

`{"rule_id":"PILOT-01","status":"generated|open_question|skipped","case_id":"API-OP-001","path":"test-cases/gates/API-OP-001.md"}`

Для `open_question` і `skipped` поля `case_id` та `path` дорівнюють `null`.

**У режимі «Дано задачу»** відповідай коротко (без повного тексту кейсів: їх оркестратор прочитає з диска), а останнім рядком виведи JSON (без обгортки в кодовий блок):

`{"key":"SKY-3","status":"generated|needs_input|failed","cases":[{"case_id":"E2E-OP-010","path":"test-cases/requests/E2E-OP-010.md","ac":[1,2]}],"skipped":[{"ac":3,"reason":"…"}],"reason":null}`

`cases` містить лише файли, записані в цьому виклику; `reason` заповнюється для `needs_input` і `failed`.
