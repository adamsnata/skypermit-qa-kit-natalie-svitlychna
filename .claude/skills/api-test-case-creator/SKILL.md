# API тест-кейси (на одне бізнес-правило)

API-кейс — перевірка **одного бізнес-правила** прямими HTTP-запитами до `/api/v1`, без UI. Для UI/E2E-кейсів (кроки через форму й `data-testid`) є скіл **`ui-test-case-creator`**; цей скіл їх не створює.

  - **`06 — Business Rules`** (851969) — правила гейтів, межі, `rule_reference` (§6);
  - **`02 — Request Lifecycle`** (720897) — стани й переходи для ланцюжків;

## Формат ID

`API-<РОЛЬ>-<NNN>`: `API-OP-011`, `API-RV-001`, `API-AN-001`, для двох ролей — `API-OP-RV-001`.

| Код | Роль |
|---|---|
| `OP` | Operator (сесія оператора, зокрема реєстрація/вхід) |
| `RV` | Reviewer (`X-Reviewer-Id`) |
| `AN` | без сесії й без `X-Reviewer-Id` (напр. перевірка `401`) |

- **ID унікальний у всьому `test-cases/`** (усі підпапки, зокрема `gates/`). Наступний номер = максимальний наявний для того самого префікса + 1. Тому нумерація «з 001» діє лише там, де префікса ще немає; зараз `API-OP-001…010` уже зайняті в `test-cases/gates/`, тож новий набір починається з `API-OP-011`. Дублі ID заборонені; пропуски не заповнюй.
- Номери для ланцюжка (див. нижче) — це **один** ID на весь ланцюжок.

## Авторизація в кроках

У кожному запиті вказуй рівно **один** спосіб автентифікації, **ніколи обидва разом**:

- **Сесія оператора** — запит виконується після `POST /api/v1/auth/login` (або реєстрації `POST /api/v1/operators`, що теж відкриває сесію); у кроці: `Авторизація: сесія оператора`.
- **Reviewer** — заголовок `X-Reviewer-Id: <значення>`; у кроці: `Авторизація: X-Reviewer-Id`. Сесії при цьому немає.
- **Без авторизації** — для `AN`-кейсів і `POST /operators`, `POST /auth/login` до входу: `Авторизація: немає`.

Пароль, токен, ключ у кейсі не пиши: `<пароль оператора>` або змінна `{{operatorPassword}}`. Унікальні дані (email, `national_id`) роби унікальними за ID кейса.

Хто яким способом має право звертатись — за `03#Authentication & authorisation` (напр. `submit`/`cancel` — лише власник-оператор; `validate` і `GET` — власник або будь-який reviewer; `approve`/`reject` — лише `X-Reviewer-Id`).

## Крок 1. Визнач правило, роль і тип кейса

Запит має називати **одне** бізнес-правило: JSON `{"gate": "TIME_WINDOW", "rule_reference": "TSD-4 §2.1", "story": "SKY-2"}` (`story` — ключ задачі Jira, опційно; іде в Rationale рядком `Задача: <key>`) або словами (гейт + умова з `06`, напр. `PILOT / сертифікація чинна 18 міс.`). Вхід `cover-gaps` (`id`, `gate`, `title`, `citation`, `open`) теж приймається: `citation` = `rule_reference`. Не вдається однозначно визначити правило чи роль — одне питання через AskUserQuestion. Якщо правило не вписується в жоден гейт чи ендпоінт — запитай, не вигадуй.

Вхід «Дано задачу» (від оркестратора `story-to-api-tests`) містить кілька AC замість одного правила: правила з AC визначай за описом у розділі «Режим «Дано задачу»» (після Кроку 4а).

Тип кейса:
- **Одиночна перевірка (BV / EP)** — `POST /flight-requests/{id}/validate` (див. «Техніки»).
- **Ланцюжок (state transition)** — кілька запитів поспіль (див. «Техніки»).

## Крок 3. Збери джерела

Прочитай `03`, `06`, `07`, `05` (і `02` для ланцюжків) повністю. Для кожного кейса зафіксуй:
- ендпоінт і метод — з реєстру `03` (`#Registry`, `#Flight requests`, `#Reviewer`);
- код відповіді — з `03#Error semantics` (`409` — перехід неможливий; `422` — бізнес-правило відмовило; `401`/`403`/`404`/`400`);
- для `422` — `failing_gate` (`PILOT`/`AIRCRAFT`/`ZONE`/`TIME_WINDOW`, **перший** гейт, що впав) і `rule_reference` **дослівно** з `06#6` (напр. `OH-1 §2.1`);
- межі й дані зон — з `06#3`, `06#4`.

Гейти йдуть у порядку `PILOT → AIRCRAFT → ZONE → TIME_WINDOW` і зупиняються на першому збої. Тому у кейсі на гейт N усі гейти до нього **мають проходити**, а наступні — не мають значення; передумови добирай так, щоб `failing_gate` був однозначним.

## Техніки тест-дизайну

### BV та EP — окремі атомарні перевірки через `validate`

Кожна межа й кожен клас еквівалентності — **окремий кейс** з одним запитом `POST /api/v1/flight-requests/{id}/validate` (без тіла). `validate` не змінює state, тож перевірка чиста, а `DRAFT`-заявка (її готують у Preconditions) лишається незмінною.

- **EP:** по одному кейсу на валідний і невалідний клас кожної умови правила (напр. `PILOT`: `R_BASIC` у зоні `CONTROLLED` → `422`; `R_ADVANCED` у `CONTROLLED` → `200`).
- **BV:** значення на межі, під нею й над нею; межі — лише з `06` (напр. altitude 120 / 121 м у `DNI-OPN-1`; тривалість 15 / 14 хв, 240 / 241 хв; сертифікація рівно 18 міс. / 18 міс. + 1 день; лід-тайм 6 год + 1 хв / 6 год − 1 хв; `mtom` 900 / 901 г — але `mtom > 30000 г` — це `422` на `POST /aircraft` (реєстрація), а не гейт). Для меж за часом (відносно моменту перевірки) точну межу не бери: вона нестабільна, бо між підготовкою і запитом минає час; бери ±1 хв.
- Очікуваний результат: `422` + `failing_gate` + `rule_reference` + `message` (див. нижче), або (позитивна межа) `200` — за `03`/`openapi.yaml`.
- Дані, що лише готують сценарій (оператор, пілот, ЛА, `DRAFT`-заявка), — у **Preconditions**, а не в Steps.
- Якщо потрібний стан даних API створити не дає (оператор `L2`/`L3` або `SUSPENDED`: реєстрація завжди створює `L1`, підвищення — «out-of-band admin action» за `03`) — так і напиши в Preconditions («потрібна підготовка даних: …») і Rationale; обхід не вигадуй.

### State transition — наскрізні ланцюжки

Один кейс = один ланцюжок запитів, що веде заявку через стани й перевіряє результат на кожному кроці. **Ланцюжки з state transition стануть колекцією в Postman** (скіл `postman-collection-builder`), тому:
- кожен запит ланцюжка — окремий нумерований крок із методом, шляхом, тілом, авторизацією й **очікуваним статусом цього кроку** в самому кроці;
- id сутностей, створених у ланцюжку, передавай між кроками як змінні (`{{flightRequestId}}`), а не копіюй значення;
- уся підготовка (реєстрація оператора, пілот, ЛА, створення `DRAFT`-заявки) — **лише в Preconditions**, не в Steps: ті самі правила атомарності, що в UI-кейсах. У Steps лише запити, що перевіряються.

Типові ланцюжки (стани й переходи — за `02`):
1. **Auto-rejection:** `validate` → `422` (state лишається `DRAFT`) → `GET /flight-requests/{id}` → `state = DRAFT` → `submit` → `422` → `GET` → `state = REJECTED` → повторний `submit` → `409`.
2. **Happy path:** `validate` → `200` → `submit` → `200` → `GET` → `state = UNDER_REVIEW` → (reviewer) `approve` → `APPROVED`.
3. **Заборонений перехід:** `submit` на заявці не в `DRAFT` → `409` (з `409`, а не `422`: «неможливо спробувати», `03#Error semantics`).
4. **Cancel:** переходи й дедлайн — за `06#5` (`APPROVED`, ≥ 2 год до `window_start`).

Межі ланцюжка: **до 5 кроків** (ліміт хука `validate-test-case.mjs`); останній — перевірювана дія. Довший — розбий на два кейси. Один ланцюжок — один інваріант (напр. «gate-failure при submit → REJECTED»), а не весь життєвий цикл.

## Крок 4. Перевір атомарність

- Одиночний кейс: **один** запит-перевірка й **один** результат (код + склад тіла — це одна спостережувана відповідь). Steps — 1 запит.
- Ланцюжок: кожен крок має власний очікуваний статус, але весь ланцюжок перевіряє один інваріант.
- Конкретні значення (`requested_altitude_metres = 121`, `certified_on` = дата), а не слова («забагато»).
- Перевірка розпадається на дві — створи одну, другу запропонуй окремо.

## Крок 4а. Гейт людини

Перед записом покажи **всі** кейси повністю (як у файлі) й запитай через AskUserQuestion: «Схвалити / Правити / Відхилити». Без «Схвалити» файлів не створюй (виняток: режими «Дано правило» і «Дано задачу», нижче). Для режиму «Дано правило» від `cover-gaps` (JSON `id/gate/title/citation/open`) AskUserQuestion не викликай і файли **не записуй** — поверни кейс (повний текст у блоці ```markdown), `open: true` → кейс не створюй. Пакетний гейт виконує `cover-gaps`. Номер ID обирай з урахуванням `reserved_ids` (якщо передано). У цьому режимі: роль `OP` (або `RV`, якщо правило цього вимагає); створи **один** негативний кейс — порушення правила → `422`, `failing_gate = <gate>`, `rule_reference = <citation>` (дослівно з `06#6`) через `validate`; позитивні й граничні лише запропонуй у звіті. Останнім рядком відповіді виведи JSON (без кодового блока): `{"rule_id":"PILOT-01","status":"generated|open_question|skipped","case_id":"API-OP-011","path":"test-cases/api/API-OP-011.md"}`; для `open_question` і `skipped` поля `case_id` та `path` дорівнюють `null`.

### Режим «Дано задачу»

Вхід від оркестратора `story-to-api-tests`: JSON від `jira-intake` (`key`, `title`, `check_type = "api"`, `acceptance_criteria`, …) + `doc_check` (таблиця статусів AC від `story-doc-check`); опційно `reserved_ids` і `revise: {"paths":[…],"comments":"…"}`.

- AskUserQuestion не викликай, гейт людини не виконуй: його виконує оркестратор. Файли **записуй одразу** як чернетки (Крок 5, з валідацією хука), по одному за виклик Write.
- Для кожного AC зі статусом «покрито» у `doc_check` визнач бізнес-правило (гейт + умова з `06`, `rule_reference` дослівно).
- **Перед генерацією шукай наявні кейси** на те саме правило: Glob/Grep у `test-cases/**` (лише файли `API-*.md`, зокрема `test-cases/gates/`) за `rule_reference`/гейтом + умовою. Якщо AC уже покрито (збігаються правило, умова й очікуваний результат) — **нового кейса не створюй**: додай наявний у `cases` з `"existing": true` і його `path` як є, `ac` — номери AC, які він покриває. Файл наявного кейса не змінюй і не перезаписуй. Покрито частково (напр., є одна межа з двох) — створи лише відсутні кейси. Оркестратор бере `existing`-кейси в upsert і в колекцію так само, як нові.
- Для решти AC добери кейси за техніками (BV, EP, state transition). AC зі статусом «суперечить» або «не описано» кейсів не отримують: додай їх у `skipped` із причиною.
- Роль — з AC і Doc ref (за замовчуванням `OP`). Нові файли — у `test-cases/api/`. ID — за «Формат ID», з урахуванням `reserved_ids`.
- Якщо правило, гейт чи роль не виводяться однозначно, нічого не записуй і поверни `status: "needs_input"` з питанням у `reason`.
- З `revise`: перезаписуй **лише** файли зі списку `revise.paths` (виняток із правила «наявні файли не змінюй»), застосувавши `revise.comments`. Нові кейси й `existing` у цьому виклику не повертай.
- Відповідай коротко (без повного тексту кейсів: оркестратор прочитає їх з диска), а останнім рядком виведи JSON без обгортки в кодовий блок:

`{"key":"SKY-2","status":"generated|needs_input|failed","cases":[{"case_id":"API-OP-011","path":"test-cases/api/API-OP-011.md","ac":[1,2],"existing":false},{"case_id":"API-OP-003","path":"test-cases/gates/API-OP-003.md","ac":[3],"existing":true}],"skipped":[{"ac":4,"reason":"…"}],"reason":null}`

`cases` містить файли, записані в цьому виклику (`existing: false`), і наявні кейси, що покривають AC (`existing: true`). `reason` заповнюється для `needs_input` і `failed`. Усі наявні кейси без нових — теж `status: "generated"`.

## Крок 5. Запис

Шаблон: `templates/test-case.md` (поруч із цим `SKILL.md`). Файл: `test-cases/api/<ID>.md`, лише інструментом Write, по одному файлу за виклик; перевір, що такого файлу ще немає. Поля — рівно як у шаблоні й у тому ж порядку: заголовок, Doc ref, Role(s), Preconditions (опційно), Steps, Expected result, Rationale. Нових полів не додавай.

Зразок: `examples/API-OP-001.md` (поруч із цим `SKILL.md`; негативний, з `TODO`) — звіряй лише структуру, стиль і деталізацію. У зразку навмисно немає конкретних тестових даних: добирай їх сам за правилом і Doc ref, не копіюй і не повторюй однакові значення в різних кейсах. ID в `examples/` не беруть участі в нумерації — наступний номер шукай лише в `test-cases/`.

### Формат кроку (HTTP)

```
1. `POST /api/v1/flight-requests/{{flightRequestId}}/validate`
   Авторизація: сесія оператора (власник заявки)
   Тіло: —
   → очікується: `422`   ← лише в ланцюжках; в одиночному кейсі див. Expected result
```

- Метод і шлях — як у `03` (`/api/v1/...`).
- Тіло — JSON із конкретними значеннями (або `—`). Поля — з `openapi.yaml`.
- Авторизація — рівно одна з трьох (див. вище).

### Expected result

- Для `422`: «Відповідь `422`; у тілі `failing_gate` = `<GATE>`, `rule_reference` = `<значення з 06#6>`, `message` — непорожній рядок». Усі три поля обовʼязкові; точний `message` — лише якщо він дослівно є в docs.
- Для інших кодів: код і, якщо є в docs, поля тіла (`state`, `authorisation_level` тощо).
- Без «коректно», «успішно», «як очікується» — лише спостережуваний факт.
- Для ланцюжка: підсумок наприкінці + очікуваний статус у кожному кроці; Expected result — фінальний інваріант.

### Правила заповнення

- **Заголовок:** `умова → результат`, напр. `Validate з requested_altitude_metres = 121 у DNI-OPN-1 → 422 ZONE`.
- **Doc ref:** щонайменше одне `SD/<сторінка>#<розділ>` (напр. `SD/03 — API Contract#The 422 body`, `SD/06 — Business Rules#1.3 ZONE`); для розвʼязаних питань — `SD/07 — Clarifications#<n>`; посилання на код допустиме додатково.
- **Role(s):** з `authorisation_level` і `status`, якщо впливають на результат.
- **Rationale:** правило, клас еквівалентності / межа / перехід; розвʼязані й відкриті питання; `Розбіжність із кодом: …`, якщо є; для ланцюжка — рядок `Ланцюжок: так — кандидат у колекцію Postman`.

## Крок 6. Звіт користувачу (російською, у чаті)

Коротко: шлях і ID кожного файлу; Doc ref; чи є `TODO` і розбіжності з кодом; тип (одиночний / ланцюжок); 1–3 сусідні перевірки, яких ще немає (наступні межі / класи / переходи). Якщо ID почалися не з `001` через зайняті номери — одним рядком скажи чому.
