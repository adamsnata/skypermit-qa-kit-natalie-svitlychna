# story-to-api-tests — від API-задачі Jira до кейсів, колекції Postman і звіту в Testomat.io

Оркестратор: сам нічого не пише, не перевіряє й не звертається до Jira, Confluence, Testomat чи Postman напряму. Він керує виконавцями й зупиняється на трьох гейтах людини (кроки 2, 4 і 6); запуск колекції додатково підтверджує сам `postman-cli-run` («запускай»).

Це копія `story-to-tests` для `check_type = api`. `story-to-tests` цей скіл не змінює.

| Крок | Виконавець | Як запускається |
|---|---|---|
| 1 | скіл `jira-intake` | Skill (вивід — один малий JSON) |
| 2 | скіл `story-doc-check`, агент `implementation-check` | Agent `general-purpose` для скіла (щоб Confluence-сторінки не потрапили в цей контекст), Agent `implementation-check` напряму; обидва паралельно |
| 3 | скіл `api-test-case-creator` (режим «Дано задачу»), агент `tc-verifier` з `mode: api` | Agent `general-purpose` для скіла; Agent `tc-verifier` на кожен кейс |
| 5 | скіл `testomat-sync` (`upsert`, `run`) | Skill |
| 6 | скіл `postman-collection-builder` | Skill |
| 7 | скіл `postman-cli-run`, потім `testomat-sync` (`report`) | Skill |

Від субагентів оркестратор отримує лише підсумок: таблицю/JSON і рядок підсумку. Не проси їх повертати вміст сторінок Confluence чи повні тексти кейсів.

## Не завершуй хід між кроками

Після кожного виклику скіла чи агента не завершуй хід і не віддавай його користувачу без питання. Розбери результат і одразу переходи до наступного кроку або до гейту (AskUserQuestion). Хід завершується лише так:
- після питання AskUserQuestion на гейті;
- у гілці зупинки, описаній у кроці (з підсумком за розділом «Підсумок»);
- після кроку 7 і підсумку.

JSON, який повернув скіл чи агент, є внутрішнім результатом: не виводь його в чат окремою відповіддю, показуй користувачеві лише те, що вимагає крок.

## Конфіг

- Suite у Testomat: `SkyPermit API` (`file_type: "file"`, це робить `testomat-sync`).
- Назва рана: `<key> · API`, напр. `SKY-2 · API`.
- Назва колекції Postman: `<key> · API`; environment `<назва колекції> — local` створює builder.
- Workspace Postman: `postman-collection-builder` шукає за назвою «SkyPermit» сам; оркестратор `workspace_id` не передає.
- Максимум спроб `api-test-case-creator` на один запуск: **2**.

## Обмеження

- `../skypermit` — лише читання. Нічого там не створюй, не змінюй, не запускай.
- Jira, Confluence — лише читання. Жодних git-операцій і встановлення пакетів.
- Команди виконуй з кореня цього репозиторію. Перед `rm` перевір `pwd`.
- Оркестратор файлів **не пише**: інструмент `Edit` у `allowed-tools` є, але його не використовуй, правки кейсів робить лише `api-test-case-creator` у режимі `revise`. Єдина дія оркестратора над файлами — `rm` чернеток цього прогону (див. «Видалення»).
- До `mcp__testomatio__*` і `mcp__postman__*` оркестратор не звертається: усе через `testomat-sync`, `postman-collection-builder`, `postman-cli-run`.
- Секрети (пароль оператора, ключі Postman) не проси в чат і не виводь. Пароль передається змінною ОС `SKYPERMIT_OPERATOR_PASSWORD`, логін CLI — окремо в терміналі (див. крок 6).
- Падіння тестів у прогоні не виправляй: нічого не змінюй у колекції, кейсах чи даних, щоб «позеленіло».
- Увесь текст для користувача — українською. Ідентифікатори (`DRAFT`, `API-OP-011`, `422`) — як в оригіналі.

## Крок 1. Intake

Виклич скіл `jira-intake` (Skill tool) з аргументом-ключем. Збережи JSON як `task`.

JSON від `jira-intake` у чат не виводь як окрему відповідь і хід не завершуй: перевір `check_type` та інші умови зупинки нижче й, якщо жодна не спрацювала, одразу переходь до кроку 2.

Зупинись, нічого далі не запускаючи, якщо:
- `check_type` = `"ui"` → «Це UI-задача. Для UI-задач використай `/story-to-tests <ключ>`; цей скіл працює лише з API.»
- `check_type` = `null` → поясни причину з `notes` (немає мітки `ui`/`api` або обидві) і попроси виправити мітки в Jira.
- `acceptance_criteria` порожній → скажи про це й покажи `notes`.
- замість JSON прийшла помилка або порожня відповідь.

## Крок 2. Звірка з документацією і кодом, гейт 1

Запусти **паралельно** (один блок викликів):

1. `Agent` (`subagent_type: "general-purpose"`): «Виклич скіл `story-doc-check` через Skill tool з args = <task JSON>. Поверни лише таблицю статусів і рядок «Підсумок», без переказу сторінок.» Збережи як `doc_check`.
2. `Agent` (`subagent_type: "implementation-check"`): передай `task` JSON. Збережи як `impl_check`.

Покажи користувачу обидва звіти як є, потім постав одне питання через AskUserQuestion: «Продовжити / Зупинитись».

- **Зупинитись** або немає відповіді → завершуй, нічого не створюючи.
- **Продовжити**, і загальний вердикт `implementation-check` = `not_implemented` → зупинись. Поясни, чого не вистачає в коді (з `not_found`/`partial` AC і доказів агента). Кейси не створюй.
- **Продовжити** в інших випадках → крок 3. Якщо **усі** AC у `doc_check` мають статус «суперечить» або «не описано», кейси створювати нема з чого: зупинись і скажи про це.

## Крок 3. Кейси і перевірка

### 3.1. Генерація

`Agent` (`subagent_type: "general-purpose"`): «Виклич скіл `api-test-case-creator` через Skill tool з args = режим «Дано задачу»: <task JSON>, doc_check: <таблиця>, reserved_ids: <…>. Скіл сам шукає наявні кейси на те саме правило, нові пише чернетками в test-cases/api/. Поверни лише короткий підсумок і останній рядок JSON як є.» Розбери останній рядок як JSON (`status`, `cases`, `skipped`, `reason`).

- `generated` і `cases` не порожній → далі.
- `needs_input` → задай питання з `reason` через AskUserQuestion, повтори виклик із відповіддю (рахується як спроба).
- `failed`, порожній `cases` або JSON не розібраний → повтори виклик (максимум **2 спроби** загалом), додавши «попередня спроба відхилена: <причина>». Після другої невдачі зупинись і поясни.

Розділи `cases` за полем `existing`:
- `created = [{case_id, path, ac}]` — елементи з `existing: false` (нові файли **цього прогону**). Саме `created` визначає, що можна видаляти.
- `reused = [{case_id, path, ac}]` — елементи з `existing: true` (наявні кейси, що вже покривають AC). Їх не створюємо, не змінюємо й **ніколи не видаляємо**.

Далі `created` і `reused` обробляються однаково (перевірка, показ, upsert, колекція); різниться лише видалення й правки.

### 3.2. Перевірка

Для кожного кейса з `created` і `reused` запусти `Agent` (`subagent_type: "tc-verifier"`): «mode: api. Перевір тест-кейс <case_id>». Запускай паралельно. Останній рядок відповіді — `{"case_id","verdict","failed_items","silent_items"}`; не розібраний JSON → `verdict` вважай `error`, файл залиш.

Правило обробки (окремої політики за `06 — Business Rules` немає, діє таблиця `cover-gaps`):

| verdict | Дія |
|---|---|
| `pass` | Кейс лишається. |
| `fail` | Кейс із `created`: видали файл (`rm`, див. «Видалення»). Кейс із `reused`: файл **не чіпай**, лише виключи зі списку. В обох випадках у звіті — причина з `failed_items`. |
| `no-spec` | Файл **лишається**. `silent_items` додай у `open_questions` (`q_id`, якщо є). |
| `error` | Файл лишається, позначка «верифікацію не завершено» у звіті. |

## Крок 4. Гейт людини: схвалення кейсів, гейт 2

Для кожного кейса, що лишився, прочитай файл через `Read` і покажи його **повністю**, з вердиктом перевірки й позначкою «наявний» для `reused`. Додай окремо: видалені (`created`) і виключені (`reused`) після перевірки кейси з причиною, `skipped` з кроку 3.1, `open_questions`.

Постав одне питання через AskUserQuestion: «Схвалити / Правити / Відхилити».

- **Схвалити** → крок 5.
- **Правити** → запусти крок 3.1 в режимі `revise` з `{"paths":[…кейси з created, яких стосуються правки…],"comments":"<правки користувача>"}`, потім повтори 3.2 для змінених кейсів і покажи кейси знову з тим самим питанням. Оркестратор файли сам не править. Правки до `reused`-кейсів не застосовуються (скіл їх не змінює): скажи про це й запропонуй виключити такий кейс зі списку.
- **Відхилити** → видали всі чернетки, що лишилися з `created` (див. «Видалення»), нічого не пиши в Testomat і Postman, завершуй. `reused`-файли не чіпай.

Якщо після кроку 3.2 не лишилося жодного кейса, питання не став: покажи причини й завершуй.

## Крок 5. Testomat

Лише після «Схвалити». Виклик `testomat-sync` (Skill tool):

1. `upsert "SkyPermit API" <key> <файли всіх кейсів, що лишились: created і reused>`. Збережи `suite_id`, `tests[]` (`case_id`, `test_id`, `action`), `duplicates`.
2. `run "<key> · API" <test_ids із upsert>`. Збережи `run_id`. Для `API-…` кейсів `testomat-sync` ставить `kind: automated`.

`duplicates` не ігноруй: винеси у звіт, ран створюй для решти. Помилку `tests_create` не повторюй наосліп (це правило `testomat-sync`). Режим `report` тут не викликай: результати з'являться після кроку 7.

## Крок 6. Колекція Postman і гейт 3

Виклик `postman-collection-builder` (Skill tool) з args `{"key": "<key>", "files": [<шляхи всіх кейсів, що лишились>], "collection_name": "<key> · API"}`. Розбери останній рядок відповіді як JSON (`status`).

- `status: "created"` → покажи користувачу список запитів і асертів, кейси `needs_data` («потрібна підготовка даних», у прогоні будуть `skipped`) і відкриті питання з відповіді builder. Скажи: «Колекцію створено в Postman (uid …). Перегляньте її в застосунку: запити, асерти, environment». Нагадай про передумови запуску: змінна ОС `SKYPERMIT_OPERATOR_PASSWORD` задана до запуску Claude Code, `postman login` виконано в окремому терміналі; прогін створить тестові дані на `https://skypermit.vercel.app`. Постав одне питання через AskUserQuestion: «Перегляд завершено, до запуску / Зупинитись». **Зупинитись** або немає відповіді → завершуй (`stopped_at: "collection_gate"`), колекцію не видаляй, у Testomat ран залишається відкритим.
- `status: "exists"` → колекція з такою назвою вже є, нічого не створено. JSON builder у чат окремою відповіддю не виводь і хід не завершуй. Коротко покажи `collection_id`, `environment_id`, `collection_name`, попередь, що наявна колекція може не відповідати поточному набору кейсів (наприклад, мати порожні `url`), і **одразу** постав одне питання через AskUserQuestion: «Створити нову з датою в назві (Рекомендовано) / Прогнати наявну / Зупинитись». Рекомендований варіант іде першим.
  - **Створити нову з датою в назві** → без додаткових питань повтори виклик builder один раз з `collection_name` = `<key> · API <YYYY-MM-DD>` (дата — поточна, напр. `SKY-2 · API 2026-11-10`). Повторний `exists` або помилка → зупинись (`stopped_at: "collection_gate"`). Далі як для `created`.
  - **Прогнати наявну** — лише якщо `environment_id` не `null` (інакше поясни й повтори питання без цього варіанту); далі як для `created`: показ списку з пункту вище не відбувається, одразу гейт «Перегляд завершено, до запуску / Зупинитись».
  - **Зупинитись** → `stopped_at: "collection_gate"`.
- Відповідь без JSON (зупинка builder: є лише environment, не знайдено workspace, бракує полів) → зупинись, перекажи його пояснення (`stopped_at: "collection_gate"`).

## Крок 7. Запуск і звіт у Testomat

Лише після «до запуску». Виклик `postman-cli-run` (Skill tool) з args `{"key": "<key>", "collection_id": "<uid>", "environment_id": "<uid>"}`. Скіл сам покаже, що запустить, і чекатиме «запускай» користувача; оркестратор «запускай» не питає й не підставляє за користувача. Розбери останній рядок відповіді як JSON.

- `status: "not_run"` → прогін не відбувся (немає «запускай», CLI чи логіну). Передай `reason`, у Testomat нічого не звітуй, `stopped_at: "run"`. Ран у Testomat лишається відкритим; скажи, що прогін можна повторити окремо викликом `postman-cli-run`.
- `status: "completed"` → `testomat-sync report <run_id> <results>`, де `results` — масив `results[]` з відповіді як є (`case_id`, `status`, `message`; конвертацію в `test_id` робить `testomat-sync`). Збережи підсумок (`passed / failed / skipped`, `not_in_run`).
- Не розібраний JSON → не вгадуй результати, `stopped_at: "run"`, перекажи відповідь скіла.

Для `failed` покажи користувачу причину й текстову пропозицію правки з відповіді `postman-cli-run`; нічого не застосовуй.

## Видалення

Оркестратор видаляє лише файли зі списку `created` цього прогону. Перед кожним `rm` перевір, що шлях:
- є в `created` (а не в `reused`);
- починається з `test-cases/api/` і закінчується на `.md`;
- не містить `..`.

Інакше не видаляй і запиши в підсумок як помилку. Чужі кейси, `reused` і кейси з попередніх прогонів не чіпай.

## Підсумок

Після завершення (у будь-якій гілці, де щось відбулося) виведи один JSON і нижче 2–4 речення українською: що створено, що видалено чи виключено, що пішло у відкриті питання, що записано в Testomat, що показав прогін.

```json
{
  "key": "SKY-2",
  "stopped_at": null,
  "cases": [
    {"case_id": "API-OP-011", "path": "test-cases/api/API-OP-011.md", "existing": false, "verdict": "pass", "test_id": "…", "action": "created", "run_status": "passed"}
  ],
  "deleted": [{"case_id": "API-OP-012", "reason": "…"}],
  "open_questions": [],
  "suite_id": "…",
  "run_id": "…",
  "collection_id": "…",
  "run_summary": {"passed": 1, "failed": 0, "skipped": 0}
}
```

- `stopped_at`: `null`, або `"intake"` / `"step2"` / `"impl_not_implemented"` / `"step3"` / `"rejected"` / `"collection_gate"` / `"run"` — де пайплайн зупинився.
- `existing` — `true` для `reused`-кейсів. `deleted` містить видалені `created` і виключені `reused` (у `reason` вкажи, що файл не видалено).
- `test_id`, `action`, `suite_id`, `run_id` — `null`, якщо до Testomat не дійшли; `collection_id`, `run_status`, `run_summary` — `null`, якщо не дійшли до кроку 6 чи 7.
- `open_questions` заповнюй за **будь-якої** зупинки, а не лише після кроку 3.2. Збирай усе, що вже отримано від агентів до моменту зупинки:
  - `notes` з `jira-intake` про сумніви (посилання на Confluence лише текстом, назва сторінки не збігається тощо);
  - AC зі статусом «не описано» або «суперечить» з `doc_check`;
  - `questions` і AC зі статусом `not_found`/`partial` з `impl_check`;
  - `silent_items` з `tc-verifier` та `reason` з `needs_input`;
  - `open_questions` і `needs_data` з відповіді `postman-collection-builder`.
  Елемент: `{"case_id": "API-OP-011" або null, "q_id": "Q4" або null, "question": "…"}`. `case_id` = `null`, якщо питання не привʼязане до кейса. У `question` коротко вкажи джерело («doc_check, AC 5», «impl_check», «tc-verifier», «builder»). Дублі зливай в один елемент.
- Не додавай інших полів.
