# story-to-tests — від UI-задачі Jira до кейсів у Testomat.io

Оркестратор: сам нічого не пише, не перевіряє й не звертається до Jira, Confluence чи Testomat напряму. Він керує виконавцями й зупиняється на двох гейтах людини (крок 2 і крок 4).

| Крок | Виконавець | Як запускається |
|---|---|---|
| 1 | скіл `jira-intake` | Skill (у цьому контексті: вивід — один малий JSON) |
| 2 | скіл `story-doc-check`, агент `implementation-check` | Agent з `general-purpose` для скіла (щоб Confluence-сторінки не потрапили в цей контекст), Agent `implementation-check` напряму; обидва паралельно |
| 3 | скіл `ui-test-case-creator` (режим «Дано задачу»), агент `tc-verifier` | Agent з `general-purpose` для скіла; Agent `tc-verifier` на кожен кейс |
| 5 | скіл `testomat-sync` | Skill |

Оркестратор отримує від субагентів лише підсумок: таблицю/JSON і рядок підсумку. Не проси їх повертати вміст сторінок Confluence чи повні тексти кейсів.

## Конфіг

- Suite у Testomat: `SkyPermit UI` (`file_type: "file"`, це робить `testomat-sync`).
- Назва рана: `<key> · UI`, напр. `SKY-3 · UI`.
- Максимум спроб `ui-test-case-creator` на один запуск: **2**.

## Обмеження

- `C:\workspace\skypermit\` — лише читання. Нічого там не створюй, не змінюй, не запускай.
- Jira, Confluence — лише читання. Жодних git-операцій і встановлення пакетів.
- Команди виконуй з кореня цього репозиторію. Перед `rm` перевір `pwd`.
- Оркестратор файлів **не пише**. Єдина його дія над файлами — `rm` чернеток цього прогону (див. «Видалення»).
- До `mcp__testomatio__*` оркестратор не звертається: усе через `testomat-sync`.
- Увесь текст для користувача — українською. Ідентифікатори (`DRAFT`, `E2E-OP-010`, `data-testid`) — як в оригіналі.

## Крок 1. Intake

Виклич скіл `jira-intake` (Skill tool) з аргументом-ключем. Збережи JSON як `task`.

Зупинись, нічого далі не запускаючи, якщо:
- `check_type` = `"api"` → «Це API-задача. Цей скіл працює лише з UI; для API-задач використай `/story-to-api-tests <ключ>`.»
- `check_type` = `null` → поясни причину з `notes` (немає мітки `ui`/`api` або обидві) і попроси виправити мітки в Jira.
- `acceptance_criteria` порожній → скажи про це й покажи `notes`.
- замість JSON прийшла помилка або порожня відповідь.

## Крок 2. Звірка з документацією і кодом, гейт

Запусти **паралельно** (один блок викликів):

1. `Agent` (`subagent_type: "general-purpose"`): «Виклич скіл `story-doc-check` через Skill tool з args = <task JSON>. Поверни лише таблицю статусів і рядок «Підсумок», без переказу сторінок.» Збережи як `doc_check`.
2. `Agent` (`subagent_type: "implementation-check"`): передай `task` JSON. Збережи як `impl_check`.

Покажи користувачу обидва звіти як є, потім постав одне питання через AskUserQuestion: «Продовжити / Зупинитись».

- **Зупинитись** або немає відповіді → завершуй, нічого не створюючи.
- **Продовжити**, і загальний вердикт `implementation-check` = `not_implemented` → зупинись. Поясни, чого не вистачає в коді (з `not_found`/`partial` AC і доказів агента). Кейси не створюй.
- **Продовжити** в інших випадках → крок 3. Якщо **усі** AC у `doc_check` мають статус «суперечить» або «не описано», кейси створювати нема з чого: зупинись і скажи про це.

## Крок 3. Кейси і перевірка

### 3.1. Генерація

`Agent` (`subagent_type: "general-purpose"`): «Виклич скіл `ui-test-case-creator` через Skill tool з args = режим «Дано задачу»: <task JSON>, doc_check: <таблиця>, reserved_ids: <…>. Скіл сам пише чернетки в test-cases/{module}/. Поверни лише короткий підсумок і останній рядок JSON як є.» Розбери останній рядок як JSON (`status`, `cases`, `skipped`, `reason`).

- `generated` і `cases` не порожній → далі.
- `needs_input` → задай питання з `reason` через AskUserQuestion, повтори виклик із відповіддю (рахується як спроба).
- `failed`, порожній `cases` або JSON не розібраний → повтори виклик (максимум **2 спроби** загалом), додавши «попередня спроба відхилена: <причина>». Після другої невдачі зупинись і поясни.

Запиши `created = [{case_id, path, ac}]`: список файлів **цього прогону**. Саме він визначає, що можна видаляти.

### 3.2. Перевірка

Для кожного кейса з `created` запусти `Agent` (`subagent_type: "tc-verifier"`): «Перевір тест-кейс <case_id>». Запускай паралельно. Останній рядок відповіді — `{"case_id","verdict","failed_items","silent_items"}`; не розібраний JSON → `verdict` вважай `error`, файл залиш.

Правило обробки (за `06 — Business Rules` сторінки задачі окремої політики немає, діє таблиця `cover-gaps`):

| verdict | Дія |
|---|---|
| `pass` | Кейс лишається. |
| `fail` | Видали файл (`rm`, див. «Видалення»). У звіті: причина з `failed_items`. Кейс виключається зі списку. |
| `no-spec` | Файл **лишається**. `silent_items` додай у `open_questions` (`q_id`, якщо є). |
| `error` | Файл лишається, позначка «верифікацію не завершено» у звіті. |

## Крок 4. Гейт людини

Для кожного кейса, що лишився, прочитай файл через `Read` і покажи його **повністю**, з вердиктом перевірки. Додай окремо: видалені після перевірки кейси з причиною, `skipped` з кроку 3.1, `open_questions`.

Постав одне питання через AskUserQuestion: «Схвалити / Правити / Відхилити».

- **Схвалити** → крок 5.
- **Правити** → запусти крок 3.1 в режимі `revise` з `{"paths":[…кейси, яких стосуються правки…],"comments":"<правки користувача>"}`, потім повтори 3.2 для змінених кейсів і покажи кейси знову з тим самим питанням. Оркестратор файли сам не править.
- **Відхилити** → видали всі чернетки, що лишилися з `created` (див. «Видалення»), нічого не пиши в Testomat, завершуй.

Якщо після кроку 3.2 не лишилося жодного кейса, питання не став: покажи причини й завершуй.

## Крок 5. Testomat

Лише після «Схвалити». Виклик `testomat-sync` (Skill tool):

1. `upsert "SkyPermit UI" <key> <файли кейсів, що лишились>`. Збережи `suite_id`, `tests[]` (`case_id`, `test_id`, `action`), `duplicates`.
2. `run "<key> · UI" <test_ids із upsert>`. Збережи `run_id`.

`duplicates` не ігноруй: винеси у звіт, ран створюй для решти. Режим `report` не викликай: результати прогонів з'являться пізніше. Помилку `tests_create` не повторюй наосліп (це правило `testomat-sync`).

## Видалення

Оркестратор видаляє лише файли зі списку `created` цього прогону. Перед кожним `rm` перевір, що шлях:
- є в `created`;
- починається з `test-cases/` і закінчується на `.md`;
- не містить `..`.

Інакше не видаляй і запиши в підсумок як помилку. Чужі кейси й кейси з попередніх прогонів не чіпай.

## Підсумок

Після завершення (у будь-якій гілці, де щось відбулося) виведи один JSON і нижче 2–4 речення українською: що створено, що видалено, що пішло у відкриті питання, що записано в Testomat.

```json
{
  "key": "SKY-3",
  "stopped_at": null,
  "cases": [
    {"case_id": "E2E-OP-010", "path": "test-cases/requests/E2E-OP-010.md", "verdict": "pass", "test_id": "…", "action": "created"}
  ],
  "deleted": [{"case_id": "E2E-OP-011", "reason": "…"}],
  "open_questions": [],
  "suite_id": "…",
  "run_id": "…"
}
```

- `stopped_at`: `null`, або `"intake"` / `"step2"` / `"impl_not_implemented"` / `"step3"` / `"rejected"` — де пайплайн зупинився.
- `test_id`, `action`, `suite_id`, `run_id` — `null`, якщо до Testomat не дійшли.
- `open_questions` заповнюй за **будь-якої** зупинки (`intake`, `step2`, `impl_not_implemented`, `step3`, `rejected`), а не лише після кроку 3.2. Збирай усе, що вже отримано від агентів до моменту зупинки:
  - `notes` з `jira-intake` про сумніви (посилання на Confluence лише текстом, назва сторінки не збігається тощо);
  - AC зі статусом «не описано» або «суперечить» з `doc_check`;
  - `questions` і AC зі статусом `not_found`/`partial` з `impl_check`;
  - `silent_items` з `tc-verifier` та `reason` з `needs_input`.
  Елемент: `{"case_id": "E2E-OP-010" або null, "q_id": "Q4" або null, "question": "…"}`. `case_id` = `null`, якщо питання не привʼязане до кейса. У `question` коротко вкажи джерело («doc_check, AC 5», «impl_check», «tc-verifier»). Дублі зливай в один елемент.
- Не додавай інших полів.
