# Тест-план: Frontend — портал оператора и очередь ревьюера

**Источник:** `docs/04-frontend-spec.md` · **Дата:** 2026-10-22 · **Версия:** 1.0

## 1. Объём тестирования
**Входит:** логин/регистрация оператора и сессия, реестры пилотов и ЛА, форма заявки и «Check before submitting», «My requests» и детали заявки, очередь ревьюера (approve/reject), контракт `data-testid`, отсутствие пре-фильтрации пикеров
**Не входит:** визуальный дизайн (явно минимальный), логика гейтов на бэкенде (`06`), повышение `authorisation_level` (админ-действие вне UI), автотесты

## 2. Подход к тестированию
| Вид | Техника | Источник |
|---|---|---|
| Функциональное (UI) | сценарии по экранам, позитивные потоки | `04#Operator portal`, `04#Reviewer queue` |
| Безопасность / доступ | таблица решений: роль × сессия × чужие данные | `04#Operator portal`, `03#Authentication & authorisation` |
| Негативное | классы эквивалентности + граничные значения полей | `04#Operator portal` (форма заявки, регистрация) |
| Контракт селекторов | чек-лист `data-testid` по всем элементам | `04#Two contracts to hold exactly` |
| Бизнес-правила в UI | заведомо невалидные комбинации пикеров | `04#Two contracts…` (form does not pre-filter) |

## 4. Критерии начала и окончания
**Начало:** фронтенд и API развёрнуты на стенде, доступна Supabase Auth, заведены зоны и тестовые операторы
**Окончание:** все кейсы «Высокий» выполнены и пройдены, нет открытых дефектов Critical/High, открытые вопросы зафиксированы

## 5. Окружение и тестовые данные
- Стенд с фронтендом, API и Supabase Auth; актуальные Chrome/Firefox
- Роли: 2 оператора (`L1` и выше, свои пилоты/ЛА), ревьюер с `X-Reviewer-Id` в шапке
- Данные: активная/неактивная зона, ЛА разных весовых классов, заявки во всех state
- Заявки, гарантированно падающие на каждом из гейтов `PILOT`/`AIRCRAFT`/`ZONE`/`TIME_WINDOW`

## 6. Риски
| Риск | Как снижаем |
|---|---|
| Нет полного списка `data-testid` — нечем сверять | Снять инвентарь элементов, согласовать как эталон |
| Переход на сессию: остатки «ручного» operator ID в UI | Отдельные проверки скрытия/удаления старых элементов |
| Ревьюер без логина — любой ID в шапке даёт доступ | Негативные кейсы с пустым/чужим/некорректным ID |
| Поведение UI для `SUSPENDED` оператора не определено | Фиксировать фактическое поведение, не считать эталоном |

## 7. Открытые вопросы
- Q4 (`05`) — код/тело ответа для `SUSPENDED` не определены → неизвестно, что UI показывает при create/submit
- Q5 (`05`) — ссылка `ZC-2026.1 §4` для неактивной зоны не подтверждена → текст rule reference в UI
- Новый — нет полного перечня `data-testid`; неясно, какие имена считать эталонными
- Новый — доступна ли «Check before submitting» до сохранения черновика (validate требует `{id}`)
- Новый — направление сортировки очереди по умолчанию и набор state в фильтре «My requests»
- Новый — валидация `X-Reviewer-Id` в UI (формат, пустое значение) не описана
