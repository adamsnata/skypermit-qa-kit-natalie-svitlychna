# Тест-план: API Contract (`/api/v1`)

**Джерело:** `docs/03-api-contract.md` · **Дата:** 2026-10-23 · **Версія:** 1.0

## 1. Обсяг тестування
**Входить:** auth-ендпоінти (`/operators`, `/auth/*`) і сесія, авторизація `401`/`403` і reviewer-or-owner читання, Registry/Reference data (1–8, `GET /pilots`, `GET /aircraft`), Flight requests (9–14) і Reviewer (15–16), семантика помилок і тіло `422`, порядок гейтів
**Не входить:** детальна логіка кожного гейту (`06-business-rules.md`), UI (`04`), CRUD зон (немає в API, seed-дані), підвищення `authorisation_level` (поза API), навантаження й автотести

## 2. Підхід до тестування
| Вид | Техніка | Джерело |
|---|---|---|
| API-контракт | перевірка метод/шлях/статус/тіло за таблицями ендпоінтів | `03#Registry`, `03#Flight requests` |
| Безпека / доступ | таблиця рішень: сесія × `X-Reviewer-Id` × власник ресурсу | `03#Authentication & authorisation` |
| Негативне | класи еквівалентності: зламане тіло, немає сутності, чужий ресурс | `03#Error semantics` |
| Переходи станів | виклики submit/cancel/approve/reject з кожного state | `03#Flight requests`, `03#Reviewer` |
| Бізнес-правила | перший гейт, що впав, `rule_reference` дослівно з `06#6` | `03#Gate pipeline`, `03#The 422 body` |

## 4. Критерії початку й завершення
**Початок:** API розгорнуто, Supabase Auth доступна, зони засіяно (`seed.sql`), `06#6` затверджено як еталон `rule_reference`
**Завершення:** усі кейси «Високий» пройдено, кожен статус з `03#Error semantics` покрито щонайменше одним кейсом, відкриті питання зафіксовано

## 5. Оточення та тестові дані
- Стенд з `/api/v1`, HTTP-клієнт (Postman/curl) з підтримкою cookie
- Ролі: 2 оператори (A і B, з `L1` і підвищеним рівнем), рецензент з `X-Reviewer-Id`, анонімний виклик
- Дані: пілоти/ЛА в обох операторів, активна й неактивна зона, заявки в усіх state
- Заявки, що падають на кожному гейті та на кількох одразу (перевірка «першого»)

## 6. Ризики
| Ризик | Як знижуємо |
|---|---|
| Рецензент без логіна: будь-який `X-Reviewer-Id` дає доступ до всіх даних | Негативні кейси: порожній, довільний, разом із сесією |
| Дублювання логіки гейтів у submit і validate → розбіжності | Парні кейси: одна заявка через validate і submit |
| Плутанина `409`/`422` для перетину заявок | Окремі кейси на overlap, фіксувати фактичний код |
| `SUSPENDED`-оператор: код і тіло не визначені | Фіксувати факт, не вважати еталоном (`05#1`) |

## 7. Відкриті питання
- Q4 (`05#1`) — код/тіло для `SUSPENDED` на create/submit/approve не визначені (`403` — лише заглушка)
- Q5 (`05#2`) — `rule_reference: "ZC-2026.1 §4"` для неактивної зони не підтверджено
- Нове — перетин заявок: `409` (`03#Error semantics`) чи `422 TIME_WINDOW`, `TSD-4 §5` (`06#6`)?
- Нове — approve/reject без `X-Reviewer-Id`: `400` (`03#Reviewer`) чи `401` (`03#Error semantics`)?
- Нове — код відповіді на cancel після дедлайну (`409` чи `422`) і сам дедлайн у `03` не вказані
- Нове — запит із сесією та `X-Reviewer-Id` одночасно: чия роль застосовується до списку й запису?
- Нове — валідацію `X-Reviewer-Id` (формат, порожнє значення) не описано
