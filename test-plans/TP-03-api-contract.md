# Тест-план: API Contract (`/api/v1`)

**Источник:** `docs/03-api-contract.md` · **Дата:** 2026-10-23 · **Версия:** 1.0

## 1. Объём тестирования
**Входит:** auth-эндпоинты (`/operators`, `/auth/*`) и сессия, авторизация `401`/`403` и reviewer-or-owner чтение, Registry/Reference data (1–8, `GET /pilots`, `GET /aircraft`), Flight requests (9–14) и Reviewer (15–16), семантика ошибок и тело `422`, порядок гейтов
**Не входит:** детальная логика каждого гейта (`06-business-rules.md`), UI (`04`), CRUD зон (нет в API, seed-данные), повышение `authorisation_level` (вне API), нагрузка и автотесты

## 2. Подход к тестированию
| Вид | Техника | Источник |
|---|---|---|
| API-контракт | проверка метод/путь/статус/тело по таблицам эндпоинтов | `03#Registry`, `03#Flight requests` |
| Безопасность / доступ | таблица решений: сессия × `X-Reviewer-Id` × владелец ресурса | `03#Authentication & authorisation` |
| Негативное | классы эквивалентности: битое тело, нет сущности, чужой ресурс | `03#Error semantics` |
| Переходы состояний | вызовы submit/cancel/approve/reject из каждого state | `03#Flight requests`, `03#Reviewer` |
| Бизнес-правила | первый упавший гейт, `rule_reference` дословно из `06#6` | `03#Gate pipeline`, `03#The 422 body` |

## 3. Покрытие
| # | Что проверяем | Приоритет | Источник |
|---|---|---|---|
| 1 | `POST /operators`: Auth-user + профиль, авто-логин, всегда `L1` | Высокий | `03#Authentication & authorisation` |
| 2 | login/logout/me: cookie сессии, `GET /auth/me` без сессии → `401` | Высокий | `03#Authentication & authorisation` |
| 3 | `operator_id` только из сессии; поле/параметр клиента игнорируется | Высокий | `03#Authentication & authorisation` |
| 4 | Нет сессии → `401`; чужой ресурс → `403`; ревьюер читает любой | Высокий | `03#Authentication & authorisation` |
| 5 | `GET /flight-requests`: скоуп оператора vs ревьюер + фильтры | Высокий | `03#Flight requests` (12) |
| 6 | Create → `DRAFT`; submit → `UNDER_REVIEW`/`REJECTED`; cancel | Высокий | `03#Flight requests` (9, 10, 14) |
| 7 | `validate`: те же гейты и порядок, state не меняется, идемпотентен | Высокий | `03#Flight requests` (13) |
| 8 | approve/reject: `ReviewAction`, note обязателен, нет заголовка → `400` | Высокий | `03#Reviewer` |
| 9 | `422`: `failing_gate` первого упавшего, `rule_reference`, `message` | Высокий | `03#The 422 body`, `06#6` |
| 10 | Registry/zones: GET по id, производные поля, `404`, списки | Средний | `03#Registry`, `03#Reference data` |

## 4. Критерии начала и окончания
**Начало:** API развёрнут, Supabase Auth доступна, зоны засеяны (`seed.sql`), `06#6` утверждён как эталон `rule_reference`
**Окончание:** все кейсы «Высокий» пройдены, каждый статус из `03#Error semantics` покрыт хотя бы одним кейсом, открытые вопросы зафиксированы

## 5. Окружение и тестовые данные
- Стенд с `/api/v1`, HTTP-клиент (Postman/curl) с поддержкой cookie
- Роли: 2 оператора (A и B, с `L1` и повышенным уровнем), ревьюер с `X-Reviewer-Id`, анонимный вызов
- Данные: пилоты/ЛА у обоих операторов, активная и неактивная зона, заявки во всех state
- Заявки, падающие на каждом гейте и на нескольких сразу (проверка «первого»)

## 6. Риски
| Риск | Как снижаем |
|---|---|
| Ревьюер без логина: любой `X-Reviewer-Id` даёт доступ ко всем данным | Негативные кейсы: пустой, произвольный, вместе с сессией |
| Дублирование логики гейтов в submit и validate → расхождения | Парные кейсы: одна заявка через validate и submit |
| Путаница `409`/`422` для пересечения заявок | Отдельные кейсы на overlap, фиксировать фактический код |
| `SUSPENDED`-оператор: код и тело не определены | Фиксировать факт, не считать эталоном (`05#1`) |

## 7. Открытые вопросы
- Q4 (`05#1`) — код/тело для `SUSPENDED` на create/submit/approve не определены (`403` — лишь заглушка)
- Q5 (`05#2`) — `rule_reference: "ZC-2026.1 §4"` для неактивной зоны не подтверждён
- Новый — пересечение заявок: `409` (`03#Error semantics`) или `422 TIME_WINDOW`, `TSD-4 §5` (`06#6`)?
- Новый — approve/reject без `X-Reviewer-Id`: `400` (`03#Reviewer`) или `401` (`03#Error semantics`)?
- Новый — код ответа при cancel после дедлайна (`409` или `422`) и сам дедлайн в `03` не указаны
- Новый — запрос с сессией и `X-Reviewer-Id` одновременно: чья роль применяется к списку и записи?
- Новый — валидация `X-Reviewer-Id` (формат, пустое значение) не описана
